# Baret — QA Log

> Hale's running record, written by Hale's agent and committed to the repo: what was done in each session, piece by piece, how each thing works, every problem that came up and how it was solved. Anyone (Hale, a new agent session, Ezgin, Meriç) must be able to read this file alone and know where the QA and delivery work stands. Plan: `docs/QA_AND_DELIVERY.md`. Tasks: `tasks/FOR_HALE.md`.

## How this file is kept (rules for the agent)

1. **Read it first.** At the start of every session with Hale, read §1 and the latest entry of §3 before anything else, and tell Hale in two or three sentences where the last session stopped.
2. **Write as you go, not at the end.** After each finished piece of work (one task, one test pass, one bug hunted down), add its block to today's entry straight away. A session that ends abruptly must still leave its record.
3. **One block per piece.** Every separate thing gets its own block with the fields of the template in §4. Never fold two pieces into one line such as "tested the sites".
4. **Problems are written with their solution.** What happened (the exact error text or what was seen), what the cause turned out to be, what fixed it, and how to recognise it next time. A problem that is not solved yet is written too, marked `OPEN`, with what was already tried.
5. **Say how it works.** For anything run or set up for the first time, add or update its entry in §2: the command, what it needs, what a good result looks like. §2 is rewritten in place so it is always current; §3 is append-only history.
6. **Rewrite §1 at the end of every session.** It is a snapshot, not a history: done, in progress, blocked, next.
7. **Facts only.** Write what was run and seen, with the commit from `/health` or `git rev-parse --short HEAD`. No "should work". If something was not checked, say so.
8. **No secrets.** Never a private key, an API key, a passkey PRF value or a seed. Addresses and transaction hashes are fine.
9. **Commit it.** The log goes into the same commit as the work it describes, on the `qa` branch. English only, like every file in the repo.

A bug still goes to the owner's task file (`docs/QA_AND_DELIVERY.md` §6). Here it gets one line with its title and where it was filed.

## 2. How things work (kept current)

One entry per thing Hale has actually run. Each: what it is, the command, what it needs, what a good result looks like, known traps.

**`pnpm install --frozen-lockfile` then `pnpm check`** — lint (biome), `tsc -b`, the copy lint, and every vitest project. Needs Node ≥ 22.22, pnpm ≥ 11 (`corepack enable`). Good result: `Test Files N passed (N)`, `Tests N passed (N)`, no non-zero exit. `AbortError` stack traces from `happy-dom`'s fetch teardown print to stderr during the run; they are noise, not a failure — only the final `Test Files` / `Tests` summary line decides pass or fail. On `main` at `ca59710`: 76 files, 712 tests, ~7s.

**`pnpm contracts:test`** (`cd contracts && forge test`) — needs Foundry (`forge`, `cast`). Good result: `Ran N test suites … N tests passed, 0 failed, 0 skipped`. On `main` at `ca59710`: 9 suites, 74 tests, incl. the `PaymentGuard` fuzz and invariant tests. Leaves an untracked `contracts/foundry.lock` (forge-std's pinned rev) after the first run; harmless, not committed.

**`cast wallet new`** — generates a fresh keypair for the test wallet. The key goes in a local, gitignored `.env` at the repo root, never in a task file or the log.

**Running the server locally** — `pnpm --filter @baret/server dev`, needs `apps/server/.env` (local, gitignored): `MONAD_TESTNET_RPC_URL=https://testnet-rpc.monad.xyz`, `MONAD_TESTNET_USDC_ADDRESS=0x534b2f3A21130d7a60830c2Df862319e593943A3`, `MONAD_TESTNET_REPUTATION_REGISTRY_ADDRESS=0x7491Cb218A7b184ac50F9c2bfbd54C2a67Bfa411`; the rest of `apps/server/.env.example` can stay empty for a read-only check (Nansen, Cleanverse, KIMI all fail closed or skip cleanly without their keys). To also check the Cleanverse scenarios: add `MONAD_TESTNET_CLEANVERSE_APASS_ADDRESS=0xbA82D189540CaC9DC6FF46B6837CaC1BFdEC58B9` and `MONAD_TESTNET_CLEANVERSE_POLICY_ADDRESS=0x36489bE45fa84f70a0c2BDB11D824Be608CB12Dd`. Good result: `curl http://localhost:8080/health` answers `{"status":"ok",...}`. Useful to check a build against the real engine before trusting it against the live API: `pnpm --filter @baret/server verify:demo -- --api http://localhost:8080 --from <any address, no key needed> [--only <text>] [--skip-cleanverse]`. The public testnet RPC gets visibly slower after a day of heavy use across sessions (`REPUTATION_DATA_UNAVAILABLE`/`COMPLIANCE_DATA_UNAVAILABLE` on an otherwise-correct scenario); a retry a few seconds later usually clears it, and it is not something a code change in this repo can fix.

**Running a one-off snippet against `@baret/guard` or `@baret/agent-kit`** — `tsx` is a dependency of those packages, not hoisted to the repo root, so `pnpm exec tsx <file>` from the root fails with "Command tsx not found"; run it as `pnpm --filter @baret/server exec tsx <file>.ts` (guard pulls in cleanly there) or `pnpm --filter @baret/agent-kit exec tsx <file>.ts`. A script with top-level `await` needs an `async function main() { ... }; main();` wrapper, or `tsx` treats the file as CommonJS and throws "Top-level await is currently not supported with the cjs output format".

**Checking a showcase/wallet change in a real browser** — no `chromium-cli` on this machine; `npx playwright install chromium` (one-time, ~100s, downloads a browser) then a plain Playwright script (`chromium.launch({ args: ["--no-sandbox"] })`, `browser.newContext().newPage()`, `page.goto(...)`) from a scratch directory with its own `package.json` (`npm init -y && npm install playwright`). Start the dev server first (`pnpm --filter <app> dev &`, poll the port with `curl -sf`, no `timeout` on macOS — use a manual `until ...; do sleep 1; done` loop instead) and stop it after (`lsof -ti:<port> -sTCP:LISTEN | xargs -r kill`).

**A virtual passkey for the wallet, from a script** — works (2026-10-10). Playwright, before navigating: `const c = await context.newCDPSession(page); await c.send("WebAuthn.enable"); await c.send("WebAuthn.addVirtualAuthenticator", { options: { protocol: "ctap2", ctap2Version: "ctap2_1", transport: "internal", hasResidentKey: true, hasUserVerification: true, isUserVerified: true, hasPrf: true, automaticPresenceSimulation: true } });`. The key is `hasPrf: true` (and `ctap2_1`): the earlier attempt passed `extensions: ["prf"]`, which is not how CDP turns PRF on, and Mera answered "your passkey provider lacks a feature Mera needs". With `hasPrf`, "Create my wallet" on `https://baret-wallet.vercel.app` lands on Home with a live address in ~15 s. Traps: the authenticator lives on one tab, so a popup (the wallet window from "Check with Baret") needs its own (`context.waitForEvent("page")`, then the same two CDP calls on it) and starts as a new account; a full `page.goto` inside the wallet locks it ("The wallet is locked"), so move between its pages with the sidebar links. A virtual passkey is still no substitute for H10's real-device stateless and cross-device tests. It cannot stand in for a second device either: a credential exported with `WebAuthn.getCredentials` and added to a fresh context with `WebAuthn.addCredential` signs, but its PRF output is different (the authenticator's hmac-secret seed is not exported), so Mera answers "This passkey can't open the account". The closest a script gets is the same authenticator with the site's storage wiped: `cdp.send("Storage.clearDataForOrigin", { origin, storageTypes: "all" })`.

**Reading a live verdict off `/agents` (or any demo site) with Playwright** — click the radio inputs directly by value, not by visible label text (the Segment component's labels can be long sentences): `page.locator('input[value="strict"]').click({ force: true })` (`force` because the native input is visually hidden under the styled control). The result's words are a `<p role="status">` *inside* the panel (`#playground [role="status"]`, or the site's own result container) — the page may have an unrelated `role="status"` elsewhere (a toast root, a layout region) that a bare `page.locator('[role="status"]').first()` matches instead and always reads empty; scope the selector. Wait for the answer with `page.waitForFunction(() => el?.textContent?.trim().length > 0)`, not a fixed `waitForTimeout` — a check can take a few seconds depending on the sources it reads. Clear the status element's `textContent` before each run (`status.evaluate(el => { el.textContent = ""; })`) so a stale answer from the previous run cannot be mistaken for the new one when a check fails to update it.

**Checking a value the extension's manifest reads at build time (`apps/extension/wxt.config.ts`)** — do not just reason about it from the config source: `pnpm --filter @baret/extension build` (or `WXT_BARET_API_URL=<url> pnpm --filter @baret/extension build` to check a different value), then read `apps/extension/.output/chrome-mv3/manifest.json` directly (`python3 -c "import json; print(json.load(open('...'))['host_permissions'])"` or similar). WXT loads `.env`, `.env.local`, `.env.<mode>`, etc. from the package's own directory (here, `apps/extension/`) before the manifest callback runs, so a var set only in the repo root's `.env` is not seen; `.env.example` documents the var, an actual `.env`/`.env.local` is local and gitignored like everywhere else in this repo.
